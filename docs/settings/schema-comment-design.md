# 表注释与删除前引用检查 — 设计说明

> 状态：**已落地**  
> 归属：`settings`。表 `schema_comment`、`ref_hint`。种子写入。  
> 为后端删除服务：外键还被引用时，删除前说明被谁引用、有几条、先处理什么。  
> 引用保护的总规则见架构宪法 §3.3。落地时把「文案不点名下游切片」改成与本文一致。

---

## 0. 一句话

> **后端删除前用调用方这条连接问「谁的外键指向这行」。有引用就不删，用表注释和引用话术写成业务提示。**

---

## 1. 为什么在删除前做

SQLite 删除失败时只有 `FOREIGN KEY constraint failed`。用户看不到是哪类数据、有几条、要先处理什么。

父切片写死子表名，新子表就要改父代码，父也因此知道子表怎么存。子表名单在每次删除时向库要。

| 层 | 做什么 | 手段 |
|----|--------|------|
| 元数据发现 | 当前有哪些子表 | `sqlite_master` + `pragma_foreign_key_list` |
| 引用计数 | 这行被引用了几条 | 按发现结果拼 `COUNT(*)` |
| 业务话术 | 物理表名换成用户能读的话 | `schema_comment` 的中文名；`ref_hint` 的处理建议 |
| 删除 | 有引用则停 | 抛业务异常，调用方不执行 `DELETE` |

---

## 2. 规则

| # | 规则 |
|---|------|
| C1 | 后端删除被外键引用挡住时使用。调用方交出当前 `Session`、父表名、按列名给的键值，以及可选主语。主语是带类型词的整句，如 `基地「芜湖」`；不传时用「该记录」 |
| C2 | 父业务代码不写子表名，不 import 子 Model，不自己 `count` 子表 |
| C3 | 子表名单来自当次库的外键。新表声明外键后，下一次删除自动计入。`ref_hint` 没配到的子表仍然计入 |
| C4 | 计入 `RESTRICT`，以及外键开启时同样挡住删除的 `NO ACTION`。`CASCADE` 附属行随父删除。`SET NULL` 溯源指针删父后变空 |
| C5 | 业务名只用 `schema_comment.name_zh`。有 `ref_hint` 时，处理建议用它的 `hint`，种子写成侧栏路径「请到「…」处理」。没有话术则「请先处理{中文名}」。再没有中文名则用物理表名，并写「请联系管理员处理」 |
| C6 | 两张表由种子在启动时按键插入或更新。种子里没有的行留在库里。注释或话术下线，由同一次变更显式删除 |
| C7 | `schema_comment.slice` 用现网切片，供种子和目录。提示句用业务名 |
| C8 | 有引用就抛 `BusinessException`，调用方不删除。接口 `message` 用第 6 节全文，前端错误框直接显示。操作日志的失败原因仍是「仍被引用，不能删除」，同一段全文再写入 `detail`。检查之后、删除之前新插入的引用，由 `IntegrityError` 回滚，文案仍为「仍被引用，不能删除」，没有明细 |
| C9 | SQL 的表名、列名只用元数据，套双引号，且为普通标识符。调用方的父表名、列名只做对照，确认是普通标识符后与元数据匹配，不拼进 SQL。键值参数绑定。某个父列没有键值，原样抛出，不包成业务异常，调用方不删除 |
| C10 | 一次删除多行时，子表按父表发现一次。单列键用 `列 IN (...)`。复合键用 `(列1, 列2) IN (VALUES (?, ?), …)` |
| C11 | 该 Service 只供各切片删除在进程内调用。禁止挂路由，禁止单独的 HTTP 入口 |
| C12 | 一组外键的键是 `(child_table, pragma_foreign_key_list.id)`。`id` 只在一张子表内编号。提示按 `child_table`、`id` 升序，不按 `sqlite_master` 或 `pragma` 的返回顺序 |
| C13 | 发现、计数、读话术都用调用方传入的 `Session`。不 `commit`，不开新连接。两张话术表在主库。本次只检查主库上的父行 |
| C14 | 父表名不在当次库的 `sqlite_master` 里时，检查放行并打 warning。表在库里、只是没有挡住删除的外键，正常放行，不打 warning。父表名不要求先在 `schema_comment` 里 |
| C15 | 检查贴着这一条 `DELETE`。同一事务里先删引用行、再删父行时，不对还带着那些引用的父行提前做总检查 |

连接上已执行 `PRAGMA foreign_keys=ON`（`app/database.py`）。

## 3. 和「父不读子」

父切片 Service 不知道下游切片，也不知道子表怎么存。

设置切片这一处在删除前向引擎问「谁的外键指向这张父表、这个键」。子表名、外键列、`on_delete` 来自当次库的元数据。`ref_hint` 是话术：少一行配置，该子表仍然挡住删除，句子退到下一档。

落地时，架构宪法 §3.3「引擎拒绝、应用翻译」改为：

> 后端删除之前，由设置切片按本文做动态引用检查。接口返回第 6 节全文。操作日志的失败原因仍是「仍被引用，不能删除」，全文再写入 `detail`。父切片不写子表名。其后插入的引用落到 `IntegrityError` 时，译成「仍被引用，不能删除」。

`docs/architecture.md` 中对应句子改为指向本文。改主键仍译成「仍被引用，不能修改」，本文不覆盖。

## 4. 表

落在主库，设置切片。

### 4.1 `schema_comment`

一张物理表一行。SQLite 没有 MySQL 的 `COMMENT`，这张表是表注释。

| 列 | 含义 |
|----|------|
| `table_name` | 物理表名，主键 |
| `slice` | 现网切片 |
| `name_zh` | 中文名。提示里的业务名只取这里 |
| `name_en` | 英文说明 |

| `slice` | 现网 |
|---------|------|
| `masterdata` | 基地、项目、供应商、牌号分类 |
| `settings` | 用户、权限、系统设置、操作日志、本表、引用话术 |
| `stamping` | 冲压零件、工序、加工费、模具、检具 |
| `bom` | 材料清单、采购对象、焊接拆解、焊接费 |
| `yishiyiyi` | 基价、政策、废料价 |
| `costing` | 零件价格、钢材联动价、总成核价、引擎运行 |
| `engineering_change` | 设计变更、材料变更 |
| `llm` | 分析报告 |
| `file_trace` | 上传文件 |

`async_tasks`、`user_tokens` 在辅助库。它们的注释仍按所属切片写入主库。本次删除检查不覆盖辅助库上的父行。

种子覆盖现网每一张业务表。新增表时同一变更补一行。启动按 `table_name` 插入或更新。种子里没有的表名留在库里。下线一张表的注释，由同一次变更显式删除。

### 4.2 `ref_hint`

一条外键引用一句处理建议。业务名来自子表的 `schema_comment.name_zh`：发现得到 `vehicle_models`，用户看到「项目」。建议来自本表：`请先处理这些项目`。

| 列 | 含义 |
|----|------|
| `parent_table` | 父表物理名 |
| `child_table` | 子表物理名 |
| `hint` | 处理建议 |
| 主键 | `(parent_table, child_table)` |

同一子表挂在不同父表上时，建议可以不同，所以建议放在本表。中文名不在这里再存一份。

种子为现网挡住删除的 `RESTRICT` 引用补行。新增这类外键时同一变更补一行话术。启动按主键插入或更新。种子里没有的话术留在库里。下线由同一次变更显式删除。

## 5. 删除时怎么查

调用方传入当前 `Session`、父表名、按列名给的键值、可选主语。没有主语时用「该记录」。

现网主键不都是 `id`。基地是 `locations.location`，供应商是 `suppliers.full_name`，项目是 `(location, vehicle_model)`。材料清单头到项目的外键是这一对。键值按这些列名给。SQL 里出现的列名以元数据为准。

```text
本切片 Service 执行这一条 DELETE 之前
        │
        ▼
1. 查出指向这张父表的外键
        │
        ▼
2. 留下 RESTRICT / NO ACTION
        │
        ▼
3. 对每一组 COUNT(*)
        │
        ▼
4. 条数 > 0 ？
   ├─ 是 → 配话术，抛业务异常，不删除
   └─ 否 → 调用方执行 DELETE
```

1. **发现。** 在调用方这条连接上读 `sqlite_master`，再对每张表读 `pragma_foreign_key_list`。记下子表、子列、父列、`on_delete`、约束序号 `id`。父表名与元数据里的父表名对照。一组的键是 `(child_table, id)`。
2. **留下挡住删除的。** `RESTRICT` / `NO ACTION`。`CASCADE`、`SET NULL`、`SET DEFAULT` 不进入提示。同表自引用按 `on_delete` 判断。冲压工序、费用明细、权限行是 `CASCADE`。钢材联动价上指向基价、政策的可空溯源列是 `SET NULL`。
3. **计数。** `UNION ALL` 与 `COUNT(*)`。单行复合键为 `列1 = ? AND 列2 = ?`。多行单列键为 `列 IN (...)`。多行复合键为 `(列1, 列2) IN (VALUES (?, ?), …)`。参数绑定。同一张子表上的多条约束各计各的。
4. **话术。** 按 C5。条目前半是中文名，后半是处理建议。多条按 `child_table`、`id` 升序。
5. **有引用则停。** `BusinessException`。没有引用再由调用方 `DELETE`。检查和 `DELETE` 用同一条 `Session`、同一个事务。父表名不在 `sqlite_master` 时按 C14 放行。

## 6. 提示

下面的全文就是接口 `message`，错误框照原文显示。操作日志的失败原因仍是「仍被引用，不能删除」，同一段全文写入 `detail`。

```text
无法删除基地「芜湖」，原因如下：
  - 有 2 条项目，请到「主数据 → 项目 → 一览」处理
  - 有 1 条冲压零件价格，请到「核价 → 冲压零件价格核算 → 冲压零件价格一览」处理
请处理完以上数据后再删除。
```

「项目」「冲压零件」来自 `schema_comment.name_zh`。逗号后的建议来自 `ref_hint.hint`。

没有 `ref_hint`、表注释里有中文名：

```text
  - 有 4 条冲压零件价格，请先处理冲压零件价格
```

表注释也没有：

```text
  - 被 stamping_part_costs 表引用 4 条，请联系管理员处理
```

检查之后才插入的引用：

```text
仍被引用，不能删除
```

`BusinessException` 由全局异常处理器收成带 `message` 的响应。本文不另做错误类型。

## 7. 代码放哪

| 角色 | 位置 |
|------|------|
| 表注释 | `app/models/settings/schema_comment.py` |
| 引用话术 | `app/models/settings/ref_hint.py` |
| 种子 | `app/services/settings/schema_comment/seed.py` |
| 启动写入 | `app/bootstrap/lifecycle.py` 的现有种子步骤 |
| 发现、计数、话术 | 设置切片一处 Service。收调用方 `Session`、父表名、按列名的键值、可选主语 |
| 各切片删除 | 本切片 Service 在该条 `DELETE` 之前调用 |

没有 Router。禁止在 `app/routers/` 为表注释或引用检查开入口。用户看到的是各切片自己的删除接口返回的业务异常。

检查 SQL 在该 Service 调用的 Repository。用调用方传入的 `Session`，不 `commit`，不开新连接。父切片 Repository 不出现子表名。

## 8. 现网删除入口

这些删除在 `IntegrityError` 之后固定说「仍被引用，不能删除」。落地后改为紧挨着该条 `DELETE` 之前走本文，用户看到 §6 的提示：

- 基地、项目、供应商、牌号分类
- 冲压零件、模具零件
- 材料清单头、材料清单节点
- 设计变更回滚里要删的行。每条父行在自己的 `DELETE` 之前检查。同一事务里已经删掉的引用行不再计入
- 焊接工艺拆解

检查通过之后仍然被外键拒绝的，文案为「仍被引用，不能删除」。

改主键仍译成「仍被引用，不能修改」。本文不覆盖。
